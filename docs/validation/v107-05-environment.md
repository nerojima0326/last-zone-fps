# v107 검사 환경·실시간 시작 비용

`package.json`·잠금 파일에 개발 의존성 8종을 고정했다. `npm ci` 후 `npm run check`가 모든 `tools/check-*.cjs`, `*.mjs`를 발견하고 실행한다. 원본 ZIP/FBX 인수와 Three.js 경로도 자동으로 전달한다. 자세한 설치·실행법은 [검사 안내](../testing.md)에 있다.

새 실행기에서 원본 M4·Glock·스코프·병합 보고서 검사를 통과했다. `check-live-session.cjs`는 실제 RAF·입력·DRS를 유지하고 수동 `Game.update()` 전진을 사용하지 않는다. 훈련장에서 이동·사격·장전을 수행했고, 40명 경기에서 실제 수송기·자유낙하·낙하산·착지를 확인했다.

## 초기 측정

환경: Linux Chromium·SwiftShader, 320×180, 최저 품질, DRS 자동. 동일한 고정 난수 입력을 사용하되 각 모드는 새 브라우저에서 실행했다. 실제 휴대폰 FPS나 최적화 후 향상률을 뜻하지 않는다. 960×540·낮음 측정도 외부에 보관했지만 이 소프트웨어 렌더러에서는 0.89FPS 수준으로 진행되어 기능 검사의 기본 설정으로 사용하지 않았다.

첫 렌더 콜백 종료는 GPU의 실제 화면 표시 시각과 구분한다. 프레임당 dt 상한 때문에 소프트웨어 렌더러에서는 게임 시간이 실제 시간보다 느리게 흐른다. 경기는 게임 시간 4.40초 이탈, 8.13초 낙하산, 11.83초 착지를 실제로 거쳤다. 일시정지 없이 각 모드를 30초 이상 실행했고 DRS 호출도 매 프레임 확인했다. 메모리는 GC 시점에 따라 변하므로 최대 RSS를 누수량으로 해석하지 않는다. 단계별 브라우저 memory API와 CDP 순수 JS 힙·버퍼는 분리한다.

## 확인한 병목과 분할 준비안

`warmup()`은 현재 존재하는 뷰모델 6개를 대상으로 했다. 전체 30개를 이 함수가 새로 생성한다는 가정은 맞지 않았다. 텍스처 149장/123장은 이미 `prewarmTex` 대기열로 넘겨 여유 프레임에 한 장씩 업로드한다. 따라서 모든 텍스처를 한 번에 올리도록 다시 바꾸지 않았다.

그럼에도 동기 시작은 1초 이상이고, 첫 실제 화면까지 더 큰 정지가 관측됐다. CPU 장면 구성·셰이더 준비와 최초 GPU 자원 사용을 분리해서 개선할 여지가 있다. 권장 구현 순서는 다음과 같다.

1. `Game.start`의 플레이어·현재 장비·초기 위치를 먼저 만들고, 남은 봇·전리품·원거리 차량 생성을 RAF당 2~4ms 작업으로 나눈다. 필수 상태가 준비될 때까지 시작 오버레이를 유지하고 입력을 열어 초기화 중 상태에 접근하지 않도록 한다.
2. 시작 시 전체 VM 루트를 동기 컴파일하는 대신 현재 손·총·당장 필요한 장면 변형을 우선 준비한다. 기존 `prepareViewmodel()`의 `compileAsync` 경로를 이용해 나머지는 사용 전 준비하고, HDR 대상·MSAA·조준경 변형은 같은 상태로 컴파일한다.
3. 텍스처 대기열은 유지하되 시작 전 로딩 구간에도 작은 묶음으로 처리한다. 현재는 느린 프레임에서 업로드 조건을 만족하지 못해 대기열이 오래 남을 수 있다. 전투 중 무리하게 대기열을 비우는 방식은 피한다.
4. 같은 난수·장비·인원·해상도에서 여러 회의 시작 지연, 첫 화면, JS 힙·버퍼·RSS 최대값을 비교한 뒤 적용 범위를 정한다. 실제 Galaxy S24 FE Chrome의 성능 기록도 별도로 확인해야 향상률을 말할 수 있다.

이번 변경은 계측·실제 진행 검사·검사 환경 정리까지 적용했다. 시작 함수의 동기 계약을 바꾸는 분할 로딩은 위 근거를 포함한 후속 구현안으로 제시한다. 최종 재검사 원본은 `/workspace/artifacts/v107/full-checks`에 기록한다.
